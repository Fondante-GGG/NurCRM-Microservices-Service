# Фронт «Услуги»: всё для подключения бэкенда

Для Беки. Состояние на 17.10.2026.

## Что это

Сайт NurCRM, программа «Услуги» (барбершопы, салоны, процедурные, массаж и ещё шесть сфер). Все 16 разделов меню работают, но пока на **примерных данных в браузере** (localStorage). Сервер ещё не подключён ни к одному экрану. Задача: заменить примерные данные запросами к твоему API.

- Репозиторий: https://github.com/YTArmen/front-usluga (ветка `main`)
- Живая версия: https://front-usluga.vercel.app (обновляется сама после каждого push в `main`)
- Стек, как договаривались: Next.js 16 (App Router), React 19, TypeScript, Tailwind 4. Тексты на русском и кыргызском.

## Запуск

Нужен Node.js 20 или новее.

```bash
git clone https://github.com/YTArmen/front-usluga.git
cd front-usluga
npm install
cp .env.example .env.local    # NURCRM_API_URL — адрес твоего шлюза
npm run dev                   # http://localhost:3000
```

При первом открытии появится мастер настройки (выбор сферы). Это нормально: так начинается новый аккаунт.

Полезные адреса:

| Адрес | Что это |
|---|---|
| `/usluga/analitika` и другие `/usluga/...` | кабинет компании |
| `/booking` | публичная онлайн-запись для клиентов |
| `/support` | панель техподдержки NurCRM |

Проверки: `npx tsc --noEmit` (типы), `npm run build` (сборка), `node scripts/payroll-check.ts` (13 эталонных примеров расчёта зарплаты).

## Где что лежит

| Путь | Что там |
|---|---|
| `src/data/types.ts` | **Контракт данных.** Все сущности, которые ждёт фронт: сотрудник, услуга, клиент, запись, чек, смена, касса, схема зарплаты, начисление, ведомость, выплата, абонемент, роли доступа. Поля API лучше называть так же (в snake_case), тогда переходник будет тонким |
| `src/data/sample/seed.ts` | примерные данные; функция `makeSeed` показывает, как выглядят живые данные |
| `src/data/store.tsx` | хранилище: сейчас читает и пишет localStorage. **Здесь будет подключение к API** |
| `src/lib/payroll/calc.ts` | правила расчёта зарплаты. Это эталон: сервер должен считать один в один |
| `scripts/payroll-check.ts` | примеры с ожидаемыми суммами. Хорошо прогнать их же на сервере как приёмочные тесты |
| `src/lib/industry.ts` | десять сфер: стартовые должности, категории, услуги, режим приёма |
| `src/screens/` | экраны, по одному файлу на раздел |
| `src/lib/nurcrm.ts`, `src/app/api/auth/` | вход: браузер ходит на `/api/auth/login` фронта, тот на твой сервер, токен кладётся в httpOnly-cookie |
| `src/lib/config.ts` | `AUTH_ENABLED = false`: экран входа пока спрятан по решению владельца |

## Что нужно от сервера

Подробно, с полями и правилами, в двух ТЗ:

1. `docs/tz-beka-support-i-sfery.md` — сферы и режим приёма (запись, поток), обращения в техподдержку, панель поддержки, временный доступ на 72 часа, «войти как владелец», журнал действий поддержки.
2. `docs/tz-beka-finansy.md` — профили сфер как версии, режим `mixed`, новые виды зарплаты (за смену или час, ступенчатый процент), расчётный лист и выплаты, сторно в кассе вместо удаления, уникальные id документов и защита от дублей, роль «Бухгалтер», абонементы, делёж строки чека, согласование крупных расходов, закрытие месяца, табель, напоминания клиентам.

По твоему `API_REFERENCE.md` уже совпадает и можно подключать первым: вход, сотрудники, услуги и категории, клиенты и их документы, записи, заявки с витрины, начисления и выплаты в простом виде. Пробелы, которых нет в API, перечислены в обоих ТЗ.

## Предлагаемый порядок

1. Стейдж: твой бэк на внешнем адресе и две тестовые учётки (владелец компании и сотрудник поддержки). Без стейджа фронт на Vercel до сервера не достучится.
2. Вход: сверить формат ответа логина (где токен, где признак программы). Функции `pickToken` и `pickSection` в `src/lib/nurcrm.ts`.
3. Чтение: сотрудники, услуги, клиенты, записи. Экраны начинают показывать живые данные.
4. Запись: создание записи, закрытие чека, касса.
5. Зарплата по `calc.ts`, затем остальное из ТЗ.

Адрес сервера задаётся переменной `NURCRM_API_URL`: в `.env.local` для локального запуска, в настройках проекта на Vercel для живой версии.

## Вопросы

- Адрес стейджа и тестовые учётки.
- Формат ответа `POST /api/v1/auth/login/`: поле токена, срок жизни, refresh.
- CORS: фронт будет ходить через свой сервер (прокси Next), поэтому браузерный CORS не нужен, если ты не против такой схемы.
